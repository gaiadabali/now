# Provenance — E2.7 labelled sets

This document records where every labelled set in this directory comes
from, exactly how it was derived, and — per the task brief — states
plainly where a set is a weaker proxy than the real thing rather than
implying coverage that doesn't exist yet.

All sets are regenerated by `now-eval build-datasets` from two upstream,
read-only sources this package does not own or modify:

- `jakarta/content/extracted/articles.jsonl` (E1.1/E1.8 contract) — 4,772 published articles.
- `jakarta/site/taxonomy-mapping.json` (E1.4) — the 75 WP-category → facet mapping, machine-readable twin of `taxonomy-mapping.md`.

Generation is a pure, deterministic function of those two files (seeded
hashes of `wp_id`, no wall-clock or unseeded randomness) — re-running
`now-eval build-datasets` over unchanged sources reproduces every file
in this directory byte-for-byte. CI verifies this on every run (see
`.github/workflows/engine-eval.yml`'s "Rebuild labelled sets from
source" step).

## 0. The focus-keyword count — established from source, discrepancy explained

**The true figure is 1,136**, counted directly from
`jakarta/content/extracted/articles.jsonl`:

```
$ python -c "
import json
rows = [json.loads(l) for l in open('jakarta/content/extracted/articles.jsonl', encoding='utf-8')]
print('total rows:', len(rows))
print('status values:', {r['status'] for r in rows})
focus = [r for r in rows if r.get('meta', {}).get('_yoast_wpseo_focuskw')]
print('non-empty _yoast_wpseo_focuskw:', len(focus))
"
total rows: 4772
status values: {'publish'}
non-empty _yoast_wpseo_focuskw: 1136
```

Confirmed twice: independently by this package before receiving any
outside input, and again by an independent QA pass over the same file.
Both counts land on exactly **1,136**, and — because every one of the
4,772 rows in `articles.jsonl` already has `status == "publish"` — this
is the *same number* whether you count "all rows" or "published-only."
There is no denominator split to find here.

**Two other figures exist and neither matches:**

| Source | Figure | Status |
|---|---|---|
| `ARCHITECTURE.md` §6 / `PROGRESS.md` (original) | 1,376 | A pre-extraction estimate from a streaming gzip parse of the MariaDB dump — documented elsewhere (`extraction_report.md`) as undercounting several tables because a naive/streaming parser silently drops rows on large `post_content`/`postmeta` blobs. Superseded by the real restore. |
| E1.1 (`extraction_report.md`) | 1,465 | From a real, non-streaming MariaDB restore — described there as "always ≥ the doc figures," the opposite direction from what would explain 1,465 vs 1,136 as a subset relationship. Does **not** match the `_yoast_wpseo_focuskw` count actually present in the `articles.jsonl` artifact E1.1 itself shipped. |
| `jakarta/site/taxonomy-mapping.md` (E1.4) | 1,136 | Matches this package's direct recount of `articles.jsonl` exactly. |

**The cause of the 1,465-vs-1,136 gap is not confirmed.** The
throwaway MariaDB container E1.1 queried (`now-wp-extract-mariadb`) has
since been torn down, so its exact query cannot be re-run to find the
extra 329 rows. Plausible, unconfirmed hypotheses (recorded here so a
future investigator doesn't have to start from zero, not asserted as
fact): E1.1 may have counted raw `wp_postmeta` rows for that meta_key
across every post in the dump regardless of status (drafts, revisions,
trashed, non-`post` post types would all be present in a raw `wp_postmeta`
scan but are correctly excluded from the 4,772-row `articles.jsonl`
contract), or may have treated an empty-string meta value as
"present." Both would inflate a raw-table count above the
per-published-article figure. Neither has been verified against the
original database, which no longer exists in this environment.

**This package uses 1,136 as the number of record**, because that is
what is actually present in the frozen `articles.jsonl` contract this
whole pipeline (and E2.1/E2.2 after it) is built against — the count
that matters is "how many labels can the eval harness draw on," not a
raw table scan of rows nothing downstream will ever see.

**Does the corrected count materially shrink anything?** No labelled
set in this package was sized off the wrong (1,465 or 1,376) figure —
`facet_labels.holdout.jsonl` was built directly from `articles.jsonl`
from the start, so its size (237, see §4 below) already reflects
reality; it was never padded toward a stale target.

## 1. Hold-out split (`now_eval/datasets/split.py`)

Every set that could gate a *trainable* model (facet tagging / E2.2,
type classification / E2.1) is drawn only from a deterministic 20%
`eval` partition of `wp_id`s (`hash("now-eval-split-v1:" + wp_id) % 100
< 20`). The complementary 80% `train` partition is what E2.1/E2.2 may
fit, tune, or few-shot against — **never the specific rows in these
files.** `tests/test_split.py` proves the split is deterministic, salt-
and fraction-sensitive, and roughly matches its configured fraction.
`build_type_labels(..., split="train")` exposes the same category-prior
logic against the train partition, used only to fit the
`TrivialMostPopularSUT` baseline (so even the trivial baseline respects
the hold-out it exists to validate) — never to compute a reported
metric.

## 2. `related_articles.labelled.jsonl` — 200 queries

**Ground truth:** no "related posts" plugin data exists in the archive
(no YARPP tables; confirmed absent by grep over the E1.1/E1.7 extraction
reports). Per the task brief's own framing — treat editor-authored
metadata as the human label — this set uses
`_yoast_wpseo_primary_category`, a deliberate single-category choice a
human editor makes per article (distinct from the WP default/multi
category assignment), as the relatedness signal: two articles sharing a
primary category are labelled "related."

**Construction:** from eval-split articles with a non-empty primary
category whose category (a) is not a print-issue grouping (34 such
categories exist — magazine-issue themes, not subjects, per
`taxonomy-mapping.md` §0/§B) and (b) has at least 8 members total (so a
perfect precision@6 is achievable — an under-8 category can't fill 6
correct slots), 200 are sampled by a stable hash of `wp_id`. Each
query's relevant set is every other member of its primary category
(any split — the candidate universe a related-articles engine searches
over is the whole corpus; only which articles serve as *query seeds* is
hold-out-restricted).

**Real result:** seeds span 33 distinct categories (top: News 30,
Dining News 23, Events 22, Dining Offers 21 — see `now-eval run` output
for the full distribution).

**Known limitation, stated plainly:** primary-category overlap is
coarser than a genuine "would a person say these two specific articles
are related" judgment. It is the strongest zero-cost editorial signal
actually available today. Follow-up for whoever builds the real
related-articles rail (E3.5+): spend a small editorial pass on genuine
pairwise judgments once the surface exists, and treat this set as a
floor to beat, not a permanent ground truth.

## 3. `search_queries.provisional.jsonl` — 200 queries

**GSC caveat (task brief, explicit):** Hansel has not confirmed Google
Search Console is verified for the domain, so this harness does not
assume access. `now_eval.datasets.search_queries.load_gsc_queries` is
fully implemented and unit-tested against a synthetic export fixture
(`tests/fixtures/gsc_export_sample.csv`, shaped like a real GSC
"Queries × Pages" export) so a real export "drops in cleanly" the
moment access is confirmed — but **it has never run against real GSC
data**, because none exists in this environment. Say this plainly
rather than imply coverage: the number this harness gates on today is
the provisional set below, which is a materially weaker signal than
real query→click data.

**Construction (half focus-keyword, half title, both eval-split):**
- `source: "focus_keyword"` (100) — the editor's own SEO target phrase
  as the query; the source article graded relevance 3, same-primary-
  category peers graded 1 (weak/soft relevance so nDCG has more than
  one relevant grade to discriminate against), everything else 0.
- `source: "title"` (100) — same grading scheme, using the article's
  own title as the query, restricted to titles ≤6 words so the "query"
  stays query-shaped rather than headline-shaped. This is the *weaker*
  half of the set: nobody types a 12-word headline into a search box.
  Read `source="focus_keyword"` results as the more trustworthy half.

Neither is behavioural. Both are structural proxies for "what would a
real query→click pair look like," and both should be replaced or
supplemented by `load_gsc_queries` output the moment GSC access exists
— reported side by side, not blended silently, per the module
docstring.

## 4. `facet_labels.holdout.jsonl` — 237 labels

**Ground truth:** `_yoast_wpseo_focuskw` directly — "the editor's own
topic label," per the task brief. Restricted to the eval-split
partition (**237** of the corpus-wide 1,136 non-empty focus keywords —
see §0 above for how 1,136 was established). Normalized to a slug
(`slugify`: lower-case, non-alphanumeric runs → `-`) so it is directly
comparable to the slug-shaped facet vocabulary in
`engine/packages/taxonomy`, rather than doing fuzzy free-text matching.

**Known limitation, stated plainly:** a focus keyword is an SEO
keyphrase, not always a member of the §4 controlled facet vocabulary
(vibe/cuisine/occasion/audience/amenities/price_band/topic) — a
meaningful fraction are proper nouns (author names, people profiled in
a piece) that a correct facet tagger should *not* emit and should not
be penalized for missing. This harness reports precision/recall exactly
as specified regardless (that is the task and ARCHITECTURE.md §17's
literal ask), but whoever reads the 0.85 gate for E2.2 should know the
practical recall ceiling against *this specific* held-out set is below
1.0 for reasons unrelated to tagging quality — this is a data-quality
caveat, not a metric bug.

## 5. `type_labels.sample.jsonl` — 200 labels

**Ground truth, and the biggest stated limitation in this package:**
**this is NOT a human-reviewed sample.** No classifier and no editorial
review pass exists yet (E2.1 is not built), and no reviewer opened any
of these 200 articles individually. What exists instead is the
strongest defensible proxy available today: articles whose WP category
maps to an L1 `type` at **HIGH confidence** *and* is **not** flagged
`per_article` in `taxonomy-mapping.json` — i.e., categories the
architect's own review judged unambiguous at the article level (every
article filed under "Dining News" is a restaurant; every article filed
under "Events" is an event). Print-issue categories are excluded even
when they'd otherwise qualify (none currently do, but the code guards
against it — see `sources.CategoryPrior.type_is_category_certain`).

Qualifying categories in the real corpus: `dining-offers`(eat),
`events`(event), `dining-news`(eat), `stay-offers`(stay),
`dining-reviews`(eat), `explore-indonesia`(editorial),
`opinion`(editorial), `now-people`(editorial), `world-traveller`
(editorial), `history-heritage`(editorial), `offers`(stay),
`music`(event), `dining`(eat), `discover-jakarta`(editorial),
`hidden-heritage`(editorial), `sites-destinations`(do).

**Coverage gap, stated plainly:** no HIGH-confidence, category-certain
mapping exists for `drink`, `wellness`, or `shop` in the current
taxonomy mapping — this sample has **zero examples of those three L1
types**. A classifier that is excellent at telling a bar from a spa
would look untested by this set alone.

Sampling: eval-split candidates are grouped by type, each group capped
at 60, then trimmed to the 200-sample budget by repeatedly shrinking
the *currently largest* type group by one (never squeezing out a
smaller group to make room for an over-represented one). On the real
corpus this converges to an even **50 eat / 50 editorial / 50 event /
50 stay** split.

**Before this metric is trusted as the real ≥0.95 production gate**
(§17: "gates competitor exclusion" — a hotel misclassified as
`editorial` puts a rival on a paying client's page, per §8.A/§17 point
2), an editor should either spot-check this 200-article sample or a
true per-article reviewed sample should replace it, and `drink`/
`wellness`/`shop` coverage should be added. Flagged as a direct
follow-up for E2.1, not glossed over.

## 6. Itinerary constraint checker — spec, not a labelled set

`now_eval/metrics/itinerary.py` has no data file because the OR-Tools
solver it validates is E5 scope and doesn't exist yet. It is a
standalone, importable module (`Itinerary`, `Stop`, `PartyConstraints`,
`check_itinerary`, `check_batch`) with 22 unit tests
(`tests/test_itinerary.py`) proving each of the seven checks (venue

catches the failure mode it claims to, plus the batch-level "100%, hard

single itinerary in a batch has any violation). E5 is expected to
import this module directly in its own solver's post-generation
validation pass rather than re-implement constraint logic.

## 8. `calibration/` — F96/F97 confidence-mapping ground truth

**This directory is deliberately not covered by the "regenerated
byte-for-byte from source" guarantee §0–§7 make.** Everything above is a
pure function of two version-controlled JSONL files, verified reproducible
in CI. `calibration/` is the opposite by necessity: the task that produced
it (F96 — "the 0.85 gate compares numbers `now_classifier.confidence`
invented, never calibrated against anything") explicitly forbids
re-running classification, so this reads the *live*, already-written
classifier output straight out of `now_jakarta` / `now_bali`
(`engine.entity_terms` + `classification_reviews`) at a point in time, and
calls the shared Ollama Cloud provider for blind proxy labels. Re-running
the sampling script against the same DB state and vocabulary is
deterministic (seeded hashes, see `now_eval.calibration.strata`); re-running
it after more articles get classified, or after the DB changes, is not
expected to reproduce the same file.

**Why an LLM is involved at all, stated plainly per ARCHITECTURE.md §1
("deterministic engine decides, LLM narrates"):** the model here is a
one-time labelling aid for this evaluation, run offline by a human-invoked
script. It is never imported by, and has no path from, any runtime request
`now_classifier` or any other engine package serves. It does not replace the
deterministic classifier; it produces an *independent* opinion to measure
that classifier against.

### 8.1 The problem this exists to fix

`engine/packages/classifier/src/now_classifier/confidence.py` maps the
review pack's `high`/`medium`/`low` category labels and the keyword cue
instrument's margin to a handful of hand-picked floats (0.95/0.93/0.75/
0.72/0.45/0.40 for `type`/`format`; `location` additionally uses 0.90 for
two different mechanisms — see below). The file says so itself: "this
mapping is this ticket's own invention." `rules.confidence_gate` in both
cities' `taxonomy-review.json` gates auto-apply at `>= 0.85` against those
invented numbers, so the 70.8%/69.3% coverage split reported for E2.1 (and
the ~46,000-row combined review queue, F97+F101) is an artifact of the
mapping, not a measured property of the corpus.

**A live query of both cities confirms the mapping is not a continuous
score — it is six discrete constants with a gap.** Zero rows in either
`classification_reviews` or `engine.entity_terms` carry any `type`/`format`
confidence value in `(0.75, 0.93)`, the range that straddles the 0.85 gate:

| value | mechanism | source | side of gate |
|---|---|---|---|
| 0.95 | category-fixed, human-reviewed "high" | inferred | auto-apply |
| 0.93 | per-article keyword cue, confident (margin ≥ 2×) | ai | auto-apply |
| 0.75 | category-fixed, human-reviewed "medium" | inferred | review |
| 0.72 | per-article keyword cue, fired (margin < 2×) | ai | review |
| 0.45 | category-fixed, human-reviewed "low" | inferred | review |
| 0.40 | per-article cue abstained, category-prior fallback | inferred | review |

So "sample around the 0.85 boundary" cannot mean "articles that scored near
0.85" — none did. It means: get enough independently-labelled evidence on
each side of the gate (principally 0.75 vs. 0.93, the two values immediately
flanking it) to check whether the accuracy cliff the invented mapping
assumes is actually there.

**A parallel F101 audit found the same structure in `location` and named
the single highest-leverage number in this whole exercise.** `location` is
multi-valued (an article can carry several true locations at once) and
reuses **0.90** for two unrelated mechanisms distinguished only by
`entity_terms.source`/`classification_reviews.source`:
`LOCATION_SITE_HOME_FALLBACK` (`source="inferred"`, no signal — default to
the site's own city) and `LOCATION_LITERAL_MATCH` (`source="ai"`, a place
name actually matched in the title). More importantly: **Jakarta's
`classification_reviews` holds 1,124 rows at confidence 0.75 (Bali: 683),
and every one of them is `source="inferred"`** — i.e. a category-fixed
location, meaning `taxonomy-review.json`'s own recorded human decision
(`resolution.decided_by`), not a classifier guess, sitting under the same
invented "medium" number as the type/format case above, one gate-width
below auto-apply. Whether that number is really ~0.75-accurate or badly
under-priced gates ~1,807 rows across both cities on its own — more than
the `type` and `format` review queues combined at some cells. `location.py`
gives this stratum the largest sample of any cell in this calibration
(n=35) for that reason.

### 8.2 Sampling design (`sample.jsonl`, `location_sample.jsonl`)

**Frame:** every article's already-written `type`/`format` outcome
(`db_frame.fetch_facet_outcomes`) and every already-written `location`
proposal (`db_frame.fetch_location_outcomes`, multi-row per article),
content-joined against `<city>/content/extracted/articles.jsonl` via the
same loader (`now_taxonomy_evidence.sources`) the classifier itself reads.
Confirmed exhaustive: accepted + reviewed row counts sum to exactly
4,772 (Jakarta) / 4,429 (Bali) articles × 2 facets for `type`/`format`.

**Strata:** `(city, facet, confidence)` for `type`/`format`; `(city, source,
confidence)` for `location` (source disambiguates the overloaded 0.90 —
see 8.1). This is a discrete-value design, not an arbitrary numeric-band
design, because the mapping itself is discrete (8.1). Within a stratum,
sampling is a deterministic seeded-hash round-robin across distinct
`proposed_value`s (`strata.stratified_sample` / `location.stratified_sample`),
not a plain random draw — a stratum dominated by one value (e.g. `type=eat`
at 0.95, since `eat` is the corpus's largest category) would otherwise tell
us almost nothing about the other 8 type values sharing that confidence
number.

**Sample size per stratum** (capped at the stratum's population, never
oversampled): `type`/`format` — 25 for 0.95/0.93/0.75, 15 for 0.72, 12 for
0.45/0.40. `location` — 35 for the flagged 0.75 category-fixed-medium
stratum (the largest single cell in this calibration), 25 for 0.95
category-fixed-high, 20 for the two `ai`-sourced strata (title-match,
lead-only-match), 15 for 0.45 category-fixed-low and 0.90 site-home-fallback.

**What this buys, honestly:** a Wilson 95% CI on a per-cell accuracy at
n=25 has a half-width of roughly ±16 percentage points at p≈0.8, narrowing
to roughly ±13pp at n=35. These are wide intervals — this calibration
answers "is the invented number roughly in the right ballpark, and which
side of a cliff is it on," not "what is the accuracy to two decimal
places." Given the "a few hundred calls, not thousands" budget constraint
against a shared, weekly-rate-limited key, this is the tightest affordable
per-cell precision across the ~20 type/format cells and ~11 location cells
this design covers; a materially tighter number would need either a much
larger budget or fewer, coarser strata (which would then hide exactly the
kind of per-mechanism difference 8.1 exists to surface).

**Totals actually drawn** (see `sample.jsonl` / `location_sample.jsonl`):
420 type/format sample rows over 411 unique articles; 245 location sample
rows over 240 unique articles. 651 unique articles, 651 LLM calls total —
inside the "a few hundred" budget the task brief sets, checked against
`https://ollama.com/api/usage` before running (weekly cap at 10.5% used
before this batch).

### 8.3 Blind LLM proxy labels (`llm_labels.jsonl`, `location_llm_labels.jsonl`)

**Blindness, mechanically enforced:** `llm_client.build_prompt` /
`location.build_validation_prompt` are the only place a request to the
model is assembled, and both are unit-tested
(`tests/calibration/test_llm_client.py`,
`tests/calibration/test_location.py`) to assert the rendered prompt never
contains the WP category, the classifier's proposed value, its confidence,
or any word describing either. The model sees only: title, Yoast excerpt,
first 800 characters of cleaned body text — for `location`, plus the list
of proposed location slugs to validate (never which mechanism proposed
them, never their confidence).

**Two different LLM tasks, matched to the two facet shapes:**
- `type`/`format` (single-valued): forced-choice classification against the
  full vocabulary (`now_classifier`'s own `type`/`format` term lists,
  descriptions only — no legacy WP category names). Model: `glm-5.2`
  (`OLLAMA_CLOUD_MODEL_GENERAL`) — chosen over the `fast` tier because
  classification quality matters more than latency at this volume (~411
  calls). `max_tokens=800`: `glm-5.2` is a reasoning model that spends
  tokens on a hidden `reasoning` field before emitting the requested JSON in
  `content` — a tight budget (300, tried first) truncated before any
  content was produced at all, live-observed and worth recording so a
  future run doesn't repeat the mistake.
- `location` (multi-valued): **validation, not forced choice** — "is this
  *specific* proposed location correct, yes/no, with more than one allowed
  to be true at once." A forced single-choice design (as used for
  type/format) would systematically mismeasure this facet: a Bali Updates
  piece about a specific Lombok resort can correctly carry both `bali` and
  `lombok` simultaneously, and asking a model to pick just one would
  manufacture false disagreements against a classifier that is, in that
  case, not wrong. Model: `deepseek-v4-flash` (`OLLAMA_CLOUD_MODEL_FAST`) —
  a validation task is simpler than open classification, so the faster/
  cheaper tier is the right one here.

**Known limitation, stated plainly:** the LLM proxy label is itself
unaudited — it is a cheap, fast, independent opinion, not a certified
ground truth. That is exactly why this design does not stop at "LLM vs.
classifier agreement rate" (see 8.4's `preliminary` vs `adjudicated`
distinction) — agreement between two independent, blind instruments is
evidence, not proof, and a human still adjudicates every disagreement plus
a random control slice of agreements before any accuracy number is reported
as final.

### 8.4 Adjudication (`adjudication_queue.jsonl` + `adjudicate.html`,
`location_adjudication_queue.jsonl` + `location_adjudicate.html`)

**Every disagreement is queued unconditionally; a proportional random
control slice of agreements is queued per cell** (`adjudication.build_queue`
/ `location.build_queue`) — agreement between the classifier and a blind
LLM is necessary but not sufficient for correctness (both could share a
blind spot on a genuinely ambiguous article), so the control slice measures
agreement's own hit rate rather than assuming it is 1.0.
`now_eval.calibration.stats.estimate_cell_accuracy` blends the two: a
disagreement contributes its adjudicated truth exactly; an un-adjudicated
agreement contributes at the *rate the control slice actually measured* for
that cell, never at an assumed 100%. Total adjudication budget: 220 for
type/format, 150 for location — sized against the task brief's own math
("18,192 rows at 10s/row is ~50 hours, i.e. unreviewable") to be two orders
of magnitude smaller and to actually get finished in one sitting.

**Tool:** `adjudicate.html` / `location_adjudicate.html` are self-contained,
offline HTML files (open directly as `file://...` — not published anywhere,
since the queue carries unpublished editorial excerpts and live DB state).
Keyboard-driven (1/2/3), one item on screen at a time, progress persisted
to the browser's own `localStorage` so a closed tab loses nothing, an
"Export verdicts" button downloads the JSON `analyze.py` reads back in.
`type`/`format` items show both proposals side by side (classifier vs.
blind LLM) with three choices (classifier / LLM / neither); `location`
items are single-candidate validations (multi-valued facet — see 8.3) with
two choices (correct / not this location), showing the LLM's own verdict
and reasoning as context, never as a second competing proposal to pick
between.

**Honest status as shipped: the queue and tool are built and ready; the
adjudication itself is Hansel's to do, not something this package can do
on his behalf.** 253 items for type/format (211 disagreements + 42 control),
152 for location (98 + 54) — 405 total. At the ~10s/item pace F97 itself
uses as its yardstick, that's roughly 60-70 minutes, in one or two sittings.

### 8.5 Preliminary results (LLM-vs-classifier agreement, pre-adjudication)

**These are agreement rates, not accuracy.** No number in this section has
been through human adjudication yet — see 8.3's limitation and 8.4's
two-stage design for why that distinction is load-bearing, not a hedge.
Reported because they are already real, already measured, and already
informative, not because they are final.

**Type/format, pooled across both cities, Wilson 95% CI (n as sampled):**

| value | mechanism | type agreement | format agreement |
|---|---|---|---|
| 0.95 | category-fixed HIGH | 0.76 [0.63–0.86], n=50 | 0.56 [0.42–0.69], n=50 |
| 0.93 | cue confident | 0.52 [0.39–0.65], n=50 | 0.38 [0.26–0.52], n=50 |
| 0.75 | category-fixed MEDIUM | 0.64 [0.50–0.76], n=50 | 0.58 [0.44–0.71], n=50 |
| 0.72 | cue fired | 0.27 [0.14–0.44], n=30 | 0.30 [0.17–0.48], n=30 |
| 0.45 | category-fixed LOW | — (type: no qualifying rows) | 0.42 [0.19–0.68], n=12 |
| 0.40 | cue abstain fallback | 0.38 [0.21–0.57], n=24 | 0.25 [0.12–0.45], n=24 |

**The headline finding: 0.93's interval does not clearly exceed 0.75's —
in both facets its point estimate is lower.** The invented mapping assumes
0.93 (auto-apply) is more trustworthy than 0.75 (review); this sample gives
no support for that ordering, and some evidence against it. A live
spot-check of the type/0.93 disagreements (`jakarta:type:0.93`, 13 of 25)
shows a specific, legible failure mode, not noise: the per-article keyword
cue instrument fires on a type-associated word inside a *general editorial*
piece that is not actually about a venue of that type — "Italy — The Land
of Wines" (an editorial history of Italian wine) cued to `drink`; a whisky
brand's Indonesia market-entry news cued to `drink`; a skincare founder
profile cued to `wellness`; a fragrance-industry trend piece cued to `shop`.
The cue instrument is confusing "this word appears" with "this article is
about a venue of that type." **0.95 also lands well below the ≥0.85 the
gate treats it as clearing** (0.76 type / 0.56 format) — format in
particular looks unreliable at every confidence value sampled, which may

**A measurement confound worth naming rather than hiding:** 12 of
`category_fixed_high`'s 16 raw disagreements, and 18 of
`category_fixed_medium`'s 32, are the location values `international` or
`other` — deliberately broad, hierarchical catch-all nodes (`World
Traveller` → `international`, `Hidden Heritage` → `other`). The blind
validation prompt asks "does this specific proposed location apply," and
the model, given no notion that `international`/`other` are umbrella
parents rather than literal places, correctly-by-its-own-lights says "no,
this piece is about Thailand specifically, not 'international'" — a
prompt-design gap in this evaluation, not necessarily a classifier error.
Excluding those two values raises `category_fixed_high` to 0.89 (consistent
with the gate's own assumption for "high") and `category_fixed_medium` to
0.73 (still below the 0.85 gate, but 21 points higher than the raw number,
and closer to a defensible "medium").

**What's left of `category_fixed_medium`'s disagreement after that fix is
not obviously noise.** 11 of its remaining disagreements propose `jakarta`
for articles the LLM (correctly, on inspection) says are not about Jakarta
— several of them are visibly Bali venues ("Sofitel Bali Nusa Dua Beach
Resort", "The Stones Legian") carrying a Jakarta-fixed category. This
matches a separate, already-tracked cross-site content issue (Bali content
sitting in Jakarta's WordPress export, first surfaced as F99) rather than
a confidence-number problem — evidence that at least part of this band's
shortfall is a data-routing bug with its own owner, not something a
different number in `confidence.py` would fix.

**What this does and does not license, stated as plainly as the rest of
this file:** this is strong enough preliminary signal to say the invented
mapping's *ordering*, not just its exact numbers, is questionable (0.93 vs.
0.75), and specific enough to point at two concrete, fixable failure modes
(keyword-cue overfit on type/format; Bali/Jakarta content routing on
location) rather than a vague "the classifier is unreliable." It is **not**
enough, on its own, to write a new number into `confidence.py` — agreement
is not accuracy, the international/other case above is a live example of a
number that moved 15-21 points once actually inspected, and the task brief
is explicit that a number should not be reported without trusting it. The
405-item adjudication queue (8.4) is what converts this into a number
someone can act on; this package deliberately stops short of guessing that
number in its place.
